DESIGN PROPOSAL · SEPTEMBER 2026

A simpler network. For everyday value.

AstroAI Chain is the proposed home network for MA, MiniBTC and future ASTRO transfers: user-authorized payments, platform-funded basic transfers and connections to selected external networks.

01 / PURPOSE

Start with useful things.

Pay inside MA

Send and receive supported network assets with a signed confirmation, a transaction receipt and a clear network name.

Support everyday applications

Give developers a small set of tools for payments, balances and receipts. Add game and community use cases after the payment path is proven.

Keep the first version focused

Prioritize transfers, supply accounting, recovery and an explorer. General-purpose application deployment is a later decision.

Proposed architecture, not a live network map. A successful internal transfer does not prove that a cross-chain transfer has settled.

Global access, built in stages

Begin with a controlled validator set across separate failure domains. Expand regions and introduce independent operators after recovery and network-partition tests. Multiple servers operated by one company remain one administrative trust domain.

Reuse mature foundations

Evaluate an EVM-compatible application chain using an established consensus implementation. Reuse AstroBridge routing and MA wallet integration where suitable; keep the existing intent ledger as a separate evidence service. Final stack selection follows a prototype review.

03 / COST & ASSETS

Free to the user. Funded to operate.

The proposal is to sponsor eligible basic transfers within this network. Servers, storage, bandwidth and security still require an operating budget. Signed requests, fair-use quotas and congestion controls protect that budget. If capacity or sponsorship is unavailable, the app must say so before signing; it must not silently charge the user.

Cross-network transfers are separate

Ethereum, BNB Smart Chain, Sui, Solana and other networks apply their own fees and confirmation rules. Connecting an adapter does not remove those costs or make every asset compatible. Each route requires separate implementation and acceptance.

04 / DELIVERY PLAN

Build trust before expanding scope.

Planning estimates from a staffed project kickoff: 2–3 backend/blockchain engineers, 1 Android engineer, and shared QA, operations and external security review. Stages are cumulative, not added together. These are estimates, not launch dates.

2–4 weeks

Internal development network

Test-token transfers, signatures, receipts and a basic explorer. Demonstrate restart recovery and supply checks.

6–10 weeks

Invited test network

Connect MA, run several nodes and measure load, abuse resistance and failures. Test assets only; publish observed results.

3–6 months

Limited production pilot

Requires security review, asset rules, funded operations, backup recovery, incident procedures and real-device acceptance. Begin with narrow limits.

6–12+ months

Wider network & integrations

Add independent operators, reviewed cross-chain routes and developer tools as evidence permits. Broad permissionless operation and arbitrary apps are separate milestones.

The release gates

No double spending or replay in adversarial tests; consistent supply; recovery after node loss; clear operator control; wallet acceptance; measured capacity and cost. There is no published TPS or finality promise before measurement.

05 / CURRENT RECORD

What exists today. What comes next.

Existing reference implementation

Local AstroAI Chain source includes a hash-linked intent ledger, snapshots, contribution records and receipt hashes. It is development groundwork, not a deployed multi-validator payment system.

Payment network: proposed

Production consensus, asset transfer accounting, operator policy, sponsorship funding and audited cross-chain settlement still need implementation and acceptance. Publishing this plan does not change existing MA balances or server services.
